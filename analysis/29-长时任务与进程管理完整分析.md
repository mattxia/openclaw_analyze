### 各环节核心代码详解

#### 第1-3步：消息入口 → 模型路由

- **dispatch.ts** — `dispatchInboundMessage()` 是整个系统的消息入口，接收来自各种渠道（Slack/Discord/Telegram等）的消息
- **get-reply.ts** — `getReplyFromConfig()` 解析配置，确定使用哪个Agent、哪个模型、是否有沙箱等
- **agent-runner.ts** — `runReplyAgent()` 是Agent执行的协调者，管理followup循环、typing指示器、block-streaming等

#### 第4步：模型核心循环（Tool Loop的关键）

**[run.ts]** 中的 `runEmbeddedPiAgent()`：

- 解析模型provider/model，处理auth profiles、上下文窗口检测
- 管理重试（failover到备用model）、自动compaction（上下文窗口溢出时压缩历史）
- 每个"attempt"通过 [attempt.ts] 的 `runEmbeddedAttempt()` 执行

在 **[attempt.ts L1868]** 中构建所有工具：

```typescript
const toolsRaw = createOpenClawCodingTools({
    agentId: sessionAgentId,
    exec: { ...params.execOverrides, elevated: params.bashElevated },
    sandbox,
    // ... 大量上下文参数
});
```

**SDK内部的Tool Loop**是自动的：
1. 模型生成响应 → 包含 `tool_use` block
2. SDK解析工具调用 → 执行对应tool → 获取结果
3. 将结果作为 `tool_result` 反馈给模型
4. 模型继续生成 → 循环直到模型输出纯文本（不再调用工具）

#### 第5步：Exec工具详细流程

**[pi-tools.ts L284]** 的 `createOpenClawCodingTools()` 中创建exec工具：

```typescript
const execTool = createExecTool({
    scopeKey: options?.exec?.scopeKey ?? options?.sessionKey,
});
```

**[bash-tools.exec.ts]** 中的 `createExecTool().execute()` 处理：
1. **参数解析**：command、workdir、env、yieldMs、background、timeout、pty等
2. **提权检查**：elevated模式允许绕过沙箱在主机上执行
3. **执行目标选择**：
   - `host=sandbox` → Docker沙箱容器（默认）
   - `host=gateway` → 网关主机直接执行
   - `host=node` → 远程配对节点执行
4. **安全策略**：deny/allowlist/full
5. **后台执行**：yieldWindow控制何时将命令转入后台
6. **调用 `runExecProcess()`** 实际执行

#### 第6步：实际进程执行

**[bash-tools.exec-runtime.ts L398]** 中的 `runExecProcess()` 是真正的执行器：

1. **创建会话对象** → 注册到 [bash-process-registry.ts]
2. **构建spawn规格**：
   - **沙箱模式**：`docker exec -i <container> /bin/sh -lc "<command>"`
   - **本地模式**：直接用系统shell执行
   - **PTY模式**：使用伪终端（用于交互式命令）
3. **通过 ProcessSupervisor** 启动子进程，注册stdout/stderr回调
4. **输出管理**：chunk限制、截断、聚合存储

对于沙箱执行，Docker参数由 **[bash-tools.shared.ts L52]** 中的 `buildDockerExecArgs()` 构建：

```typescript
export function buildDockerExecArgs(params) {
    const args = ["exec", "-i"];
    // 传环境变量（通过 -e KEY=VALUE）
    for (const [key, value] of Object.entries(params.env)) {
        if (key === "PATH") continue; // PATH特殊处理
        args.push("-e", `${key}=${value}`);
    }
    // PATH通过OPENCLAW_PREPEND_PATH中间变量传递
    args.push(params.containerName, "/bin/sh", "-lc", `${pathExport}${params.command}`);
}
```

#### 第7步：环境变量继承机制

在 **[bash-tools.exec.ts L519-L537]** 中：


## 2. 长时任务支持：新进程 vs 复用进程

### 核心结论

**每次 `exec` 调用都是新起一个进程。** 证据在 [bash-tools.exec-runtime.ts] 中，`runExecProcess()` 每次调用都会：

1. `createSessionSlug()` — 生成一个**全新的** sessionId
2. 创建一个**全新的** `ProcessSession` 对象
3. 通过 `supervisor.spawn()` 启动一个**全新的**子进程

### 场景一：同步执行完成 → 模型再调 exec

```
exec("ls /tmp")           → 进程A启动 → 等待完成 → 返回结果给模型
模型分析结果
exec("python build.py")   → 进程B启动（全新）
```

**进程A已退出并被清理**，进程B是完全独立的新进程。

### 场景二：后台执行 → 模型通过 process 工具交互

这是**唯一沿用原进程的途径**：

```
exec("python server.py", background=true)
    → 进程A启动 → 立即返回 running + sessionId="abc123"
    → 模型收到: "Command still running (session abc123)"

process(poll, sessionId="abc123")
    → 轮询进程A的输出（仍是同一个进程）

process(write, sessionId="abc123", data="some input\n")
    → 向进程A的stdin写入数据（仍是同一个进程）

process(kill, sessionId="abc123")
    → 终止进程A
```

关键在 [bash-process-registry.ts] 中维护的 `runningSessions` Map，通过 sessionId 找到对应的 `ProcessSession`（包含 `child`、`stdin`、`pid` 等进程引用）。

### 对比总结

| 方式 | 是否新进程 | 场景 |
|------|-----------|------|
| 模型连续调用两次 `exec` | **是，新进程** | 第一步编译，第二步运行 |
| `exec(background=true)` + `process poll/log/write/kill` | **否，同一进程** | 启动服务器，后续查看日志、发送输入、终止 |
| `exec(yieldMs=5000)` + `process xxx` | **否，同一进程** | 等待5秒后自动转入后台，然后用process管理 |

**核心要点**：项目对长时任务的支持不是通过"进程复用"，而是通过 **background/yield 机制让进程在后台持续运行 + process 工具管理同一个进程**。如果没有使用 background/yield，每次 `exec` 都是全新进程，但沙箱容器（文件系统）是持久的。

## 3. 多次LLM输出在同一上下文中协调执行

项目通过**三层机制**支持多次 LLM 输出在同一上下文中协调执行。

### 第一层：SDK Tool Loop — 一次 prompt() 内的多轮工具调用

在 [attempt.ts L2991] 中：

```typescript
await abortable(activeSession.prompt(effectivePrompt, { images: imageResult.images }));
```

`@mariozechner/pi-coding-agent` SDK 的 `session.prompt()` 内部自动完成 Tool Loop：

```
LLM 生成 "我需要执行 ls，然后根据结果写脚本"
  ↓ 提取 tool_use(exec: "ls /tmp")
  ↓ 调用 exec 工具 → 返回 stdout/stderr
  ↓ 组装 tool_result → 反馈给 LLM
  ↓
LLM 继续生成 "创建 script.py"
  ↓ 提取 tool_use(write: "script.py", "...")
  ↓ 调用 write 工具 → 返回成功
  ↓ 组装 tool_result → 反馈给 LLM
  ↓
LLM 继续生成 "执行 script.py"
  ↓ 提取 tool_use(exec: "python script.py")
  ↓ 调用 exec 工具 → 返回执行结果
  ↓ 组装 tool_result → 反馈给 LLM
  ↓
LLM 生成最终文本回复
```

### 第二层：sessions_yield — 显式中断后继续

在 [attempt.ts L1912-L1916]：

```typescript
onYield: (message) => {
    yieldDetected = true;
    yieldMessage = message;
    queueYieldInterruptForSession?.();
    runAbortController.abort("sessions_yield");
    abortSessionForYield?.();
},
```

触发后的流程：
1. `sessions_yield` 工具被调用 → 触发 `onYield` 回调
2. 当前 `prompt()` 被优雅中断（`abort("sessions_yield")`）
3. 让步原因作为 `customType: "openclaw.sessions_yield"` 保存到会话历史
4. Followup 队列自动调度下一轮 `prompt()`
5. 下一轮开始时，模型能看到之前的完整上下文

### 第三层：Followup Queue — 自动接力调度

在 [agent-runner.ts L218-L219]：

```typescript
if (activeRunQueueAction === "enqueue-followup") {
    enqueueFollowupRun(queueKey, followupRun, resolvedQueue);
}
```

配合 [followup-runner.ts]，当一轮 `prompt()` 执行完后，系统会自动排队下一轮执行。

### Shell 进程是否复用？

| 场景 | 是否同一进程 | 机制 |
|------|-------------|------|
| 同一轮 prompt() 内两次 exec | **否，不同进程** | 每次 exec 都 supervisor.spawn() 新进程 |
| exec(background=true) → process write/kill | **是，同一进程** | 通过 sessionId 引用同一个 ProcessSession |
| 第1轮 exec → 结果给模型 → 第2轮 exec | **否，不同进程** | 跨 prompt() 调用，每次都是新 spawn |
| 沙箱容器内部 | **文件系统持久** | 第1轮写的脚本/安装的包，第2轮的进程能看到 |

## 4. 环境变量跨exec持久化机制

### 核心结论：不自动持久化

OpenClaw 没有跨 exec 调用的自动环境变量持久化机制。每次 `exec` 都是一个全新的进程，`export` 设置的环境变量不会传递给下一次 `exec`。

证据在 [bash-tools.exec.ts L519-L537]：

```typescript
const inheritedBaseEnv = coerceEnv(process.env);  // 从宿主机 process.env 继承
const baseEnv = host === "sandbox" ? inheritedBaseEnv : sanitizeHostBaseEnv(inheritedBaseEnv);
const mergedEnv = params.env ? { ...baseEnv, ...params.env } : baseEnv;

const env = sandbox
  ? buildSandboxEnv({
      defaultPath: DEFAULT_PATH,
      paramsEnv: params.env,
      sandboxEnv: sandbox.env,
      containerWorkdir: containerWorkdir ?? sandbox.containerWorkdir,
    })
  : mergedEnv;
```

每次 exec 都重新从 `process.env`（宿主机）继承，加上模型通过 `params.env` 显式传入的变量。**没有从"上一次 exec 中 export 的变量"中读取的逻辑。**

### 为什么在沙箱容器内也不行

```
容器 A (持续运行)
  │
  ├── docker exec /bin/sh -lc "export FOO=bar"    ← 进程1退出，FOO丢失
  │
  ├── docker exec /bin/sh -lc "echo $FOO"         ← 进程2启动，FOO为空
  │
  └── docker exec /bin/sh -lc "echo $FOO"         ← 进程3启动，FOO仍为空
```

`docker exec` 不像 `docker attach`，它总是启动一个新的子进程。

### 三种环境变量继承方式

#### 方式一：模型显式传递 params.env（推荐）

```
第1次 exec:
  command: "python setup.py"
  env: { DATABASE_URL: "postgresql://..." }

第2次 exec:
  command: "python run.py"
  env: { DATABASE_URL: "postgresql://..." }  // 显式传递同一个值
```

#### 方式二：写入文件 → 后续 exec 中 source（间接持久化）

```
第1次 exec:
  command: |
    export DATABASE_URL="postgresql://..."
    echo "export DATABASE_URL=$DATABASE_URL" >> /workspace/.env

第2次 exec:
  command: source /workspace/.env && python run.py
```

文件系统在沙箱容器内是持久的。

#### 方式三：后台进程 + process.write（同一进程内持续设置）

```
第1轮:
  exec(command="bash", background=true)
  → sessionId="abc123"
  → 进程 bash 在后台持续运行

  process(write, sessionId="abc123", data="export FOO=bar\n")
  → 在同一个 bash 进程中设置 FOO

  process(write, sessionId="abc123", data="echo $FOO\n")
  → 同一个 bash 进程中输出 "bar"

  sessions_yield("等待后续操作")

第2轮（followup 队列调度）:
  process(write, sessionId="abc123", data="python script.py\n")
  → FOO 仍然在同一个 bash 进程中可用
```

[writeToStdin] 的实现：

```typescript
const writeToStdin = async (stdin: WritableStdin, data: string) => {
  await new Promise<void>((resolve, reject) => {
    stdin.write(data, (err) => {
      err ? reject(err) : resolve();
    });
  });
};
```

数据直接写入到**同一个进程的 stdin**，所以该进程内的环境变量状态完全保留。

### 对比总结

| 方式 | 是否跨轮 LLM 输出 | 是否需要模型重复传递值 | 适用场景 |
|------|-------------------|----------------------|---------|
| **显式 `params.env`** | 是 | 是 | 少数几个固定变量 |
| **写文件 + source** | 是 | 否（文件持久化在容器中） | 需要多轮共享变量 |
| **后台进程 + write** | 是 | 否（同一进程内变量持久） | 交互式 shell 会话 |

## 5. 模型如何感知环境变量限制

### 现状：没有显式告知

OpenClaw **没有在系统提示词或工具描述中明确告诉模型"每次 exec 都是新的 shell，环境变量不会跨 exec 持久化"**。

#### 1. 工具描述中没有任何说明

exec 工具的 `description`（[bash-tools.exec.ts L278-L280]）：

```typescript
description:
  "Execute shell commands with background continuation. " +
  "Use yieldMs/background to continue later via process tool. " +

```

#### 2. env 参数的 Schema 没有 description

```typescript

  command: Type.String({ description: "Shell command to execute" }),   // ✅ 有描述
```

### 模型如何"知道"这个限制

| 途径 | 说明 |
|------|------|
| **训练数据/通用知识**（主要途径） | LLM 在其训练数据中已经学到 docker exec每次都启动新进程、shell export不跨进程继承等基本概念 |

## 6. process工具实现详解

### 架构总览

process 不是一个"类"，而是一个**工厂函数 `createProcessTool()` 返回的 `AgentTool` 对象**。整个架构分为三层：

```
┌──────────────────────────────────────────────────────┐
│  process 工具 (bash-tools.process.ts)                 │
│  ┌────────────────────────────────────────────────┐  │
│  │ createProcessTool() → { name, parameters,       │  │
│  │   execute(action, sessionId, ...) }              │  │
│  │                                                  │  │
│  │  10 种 action 的 switch-case 分发                 │  │
│  └──────────┬──────────┬───────────────────────────┘  │
│             │          │                               │
│    ┌────────▼──┐  ┌───▼──────────┐                    │
│    │ Registry  │  │  Supervisor  │                    │
│    │ (内存Map) │  │  (进程管理)   │                    │
│    └───────────┘  └──────────────┘                    │
└──────────────────────────────────────────────────────┘
```

### 第一层：bash-process-registry — 会话注册表

用**两个内存 Map** 管理所有会话：

```typescript
const runningSessions = new Map<string, ProcessSession>();
const finishedSessions = new Map<string, FinishedSession>();
```

#### ProcessSession（运行中的会话）

```typescript
export interface ProcessSession {
  id: string;                      // 唯一会话ID
  command: string;                 // 原始命令
  scopeKey?: string;               // 隔离键（按 agent/session 隔离）
  child?: ChildProcessWithoutNullStreams;  // Node.js 子进程引用
  stdin?: SessionStdin;            // 可写 stdin 接口
  pid?: number;                    // 进程 PID
  startedAt: number;               // 启动时间戳
  cwd?: string;                    // 工作目录
  // 输出管理
  maxOutputChars: number;          // 总输出上限（默认 200,000）
  pendingStdout: string[];         // 待消费的 stdout 缓冲区
  pendingStderr: string[];         // 待消费的 stderr 缓冲区
  aggregated: string;              // 聚合的全部输出
  tail: string;                    // 尾部输出（最后2000字符）
  // 退出状态
  exited: boolean;
  exitCode?: number | null;
  exitSignal?: NodeJS.Signals | number | null;
  truncated: boolean;
  backgrounded: boolean;
}
```

#### 核心 API

| 函数 | 作用 |
|------|------|
| `createSessionSlug()` | 生成唯一会话 ID |
| `addSession(session)` | 注册运行中会话 |
| `getSession(id)` | 按 ID 查找运行中会话 |
| `appendOutput(session, stream, chunk)` | 追加输出、处理截断 |
| `drainSession(session)` | 排空 stdout/stderr 缓冲区 |
| `markExited(session, code, signal, status)` | 标记退出，移到 finishedSessions |
| `markBackgrounded(session)` | 标记为后台模式 |
| `deleteSession(id)` | 删除会话 |

`appendOutput` 实现了输出管理的关键逻辑：

```typescript
export function appendOutput(session, stream, chunk) {
    // 1. 追加到 pending buffer
    session.pendingStdout.push(chunk);
    
    // 2. 超限截断 (pendingCap ≤ maxOutputChars)
    if (pendingChars > pendingCap) {
        session.truncated = true;
        capPendingBuffer(buffer, pendingChars, pendingCap);
    }
    
    // 3. 追加到 aggregated（总输出上限是 maxOutputChars：20万）
    session.aggregated = trimWithCap(session.aggregated + chunk, session.maxOutputChars);
    
    // 4. 更新 tail（最后 2000 字符的快照）
    session.tail = tail(session.aggregated, 2000);
}
```

**sweeper 计时清理器**：每 `TTL/6` 毫秒运行一次，清理过期的已完成会话：

```typescript
const DEFAULT_JOB_TTL_MS = 30 * 60 * 1000;  // 默认 30 分钟

function pruneFinishedSessions() {
    const cutoff = Date.now() - jobTtlMs;
    for (const [id, session] of finishedSessions.entries()) {
        if (session.endedAt < cutoff) {
            finishedSessions.delete(id);
        }
    }
}
```

### 第二层：ProcessSupervisor — 进程管理器

管理子进程的完整生命周期。关键数据结构：

```typescript
const active = new Map<string, ActiveRun>();  // 当前活跃的运行
const registry = createRunRegistry();          // 状态历史记录
```

核心方法：

| 方法 | 作用 |
|------|------|
| `spawn(input)` | 启动新进程，返回 `ManagedRun` |
| `cancel(runId, reason)` | 取消指定进程 |
| `cancelScope(scopeKey, reason)` | 批量取消同一作用域的进程 |
| `getRecord(runId)` | 查询运行记录 |

`spawn` 支持两种模式：
- **child 模式**：普通子进程，通过 `child_process.spawn()` 启动
- **pty 模式**：伪终端，用于需要 TTY 的交互式命令

三种超时机制：
- **overall-timeout**：总执行超时
- **no-output-timeout**：无输出超时
- **scope-level cancel**：同作用域互斥

### 第三层：bash-tools.process.ts — process 工具自身

`createProcessTool()` 返回的 `AgentTool` 对象有三个要素：

**description**: `"Manage running exec sessions: list, poll, log, write, send-keys, submit, paste, kill."`

**10 种 action 的 switch-case 分发**：

```
action = "list"     → listRunningSessions() + listFinishedSessions()
action = "poll"     → getSession() → drainSession() → 返回输出
action = "log"      → sliceLogLines(offset, limit) → 分页查看
action = "write"    → resolveBackgroundedWritableStdin() → writeToStdin()
action = "send-keys"→ encodeKeySequence() → writeToStdin()
action = "submit"   → writeToStdin("\r")  (发送回车)
action = "paste"    → encodePaste() → writeToStdin()
action = "kill"     → supervisor.cancel() → 备用 killProcessTree()
action = "clear"    → deleteSession()
action = "remove"   → cancel + delete (强制移除)
```

`resolveBackgroundedWritableStdin()` 是 stdin 操作的前置校验：

```typescript
const resolveBackgroundedWritableStdin = () => {
    if (!scopedSession) return { ok: false, result: "No active session found" };
    if (!scopedSession.backgrounded) return { ok: false, result: "not backgrounded" };
    const stdin = scopedSession.stdin ?? scopedSession.child?.stdin;
    if (!stdin || stdin.destroyed) return { ok: false, result: "stdin not writable" };
    return { ok: true, session: scopedSession, stdin };
};
```

`writeToStdin` 将回调风格的 stream API 包装为 Promise：

```typescript
const writeToStdin = async (stdin, data) => {
    await new Promise<void>((resolve, reject) => {
        stdin.write(data, (err) => err ? reject(err) : resolve());
    });
};
```

### 设计要点

1. **不是类，是工厂函数**：`createProcessTool()` 返回符合 `AgentTool` 接口的对象
2. **内存 Map 注册表**：所有会话存在 runningSessions/finishedSessions Map 中，不依赖数据库
3. **stdin 直接引用**：通过持有 Node.js `ChildProcess.stdin` 引用，实现对后台进程的跨轮次写入
4. **双层输出缓冲**：pendingStdout/Stderr（待消费）+ aggregated（聚合），poll 消费前者，log 读取后者
5. **超时 + TTL 双层清理**：supervisor 管理进程超时，sweeper 清理过期已完成会话
6. **scopeKey 隔离**：不同 agent 的进程彼此不可见

```
       ═══ Followup Queue 调度 ═══

T0+10s 第二轮 prompt() 开始 (带让步上下文)
T0+12s 回合4: process(poll, "abc123")             ← 查看进程B的输出

```

### 三个独立循环的嵌套

1. **SDK Tool Loop**（最内层）：一次 `prompt()` 内，LLM ↔ 工具调用的多轮交替
2. **sessions_yield + Followup Queue**（中间层）：跨 `prompt()` 的接力执行，让步上下文持久化到会话历史
3. **ProcessSession 跨轮存续**（最外层）：背景进程通过 `runningSessions` Map 持有真实进程引用，跨越多轮 `prompt()` 持续存活
